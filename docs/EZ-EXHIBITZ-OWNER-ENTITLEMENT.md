# EZ EXHIBITZ — owner entitlement

Status: **instructed**, not implemented, not verified. Written by `mind` under
`docs/MIND-AUTHORITY.md`. The `ezxhibitz` source is not in this repository, so every
claim about the existing gate below is a requirement, not an observation.

## 1. What is being asked for

A permanent owner entitlement that survives IP changes, browser changes and the
ordinary restrictions applied to customers, and that is separate from Founder and
Professional access. It must be validated server-side from a credential. Recognition
by IP address, user-agent or any other attribute of the connection is not acceptable:
those fail on a new network or a new laptop, and they are guessable by anyone who can
see one of the owner's requests.

## 2. Two axes, kept apart

| axis | values | what it governs |
| --- | --- | --- |
| `role` | `customer`, `owner` | authority |
| `plan` | `free`, `founder`, `professional` | the commercial tier |

Owner is a role, not a high plan. Keep the axes separate so a plan change never
grants authority, and so the checks read one capability table. If the gate as
deployed already has a single decision function, the role belongs inside it rather
than beside it.

Owner is also not admin. Entitlement buys gated features for the owner's own use; it
does not let the owner read or write another customer's records. Those stay behind
whatever admin credential already guards them, unchanged.

## 3. The credential

Two Worker secrets, both set by the owner with `wrangler secret put`, neither ever
written into a file, a command, a commit, a chat or client code:

- `OWNER_ACCESS_CODE` — the code itself. At least 32 bytes of entropy, generated by
  the owner (base32 or hex). Never transmitted after the exchange in §4.
- `OWNER_SESSION_KEY` — the HMAC key used to sign sessions. Separate from the code so
  that sessions can be invalidated without changing it.

The code is presented in a request header, never in a query string, path segment or
fragment, so it cannot reach referrers, proxy logs or access logs. Compare it in
constant time — hash both sides and compare the digests, or compare equal-length
buffers with `crypto.timingSafeEqual` — after normalising to avoid length leaks.

A wrong code gets one generic `401` with no body beyond a stable error code. Never
reveal whether a code exists, how close it was, or whether owner access is configured
at all. Rate-limit attempts per source (for example five per minute) with backoff, and
keep that limiter active for the owner path too.

## 4. Session exchange

The code is exchanged once for a session, so it crosses the wire approximately never.

`POST /api/owner/session` — the name is provisional; map it onto the gate's own
routing convention — takes the code in the header, verifies it, and sets a cookie:

- `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, `Max-Age` no longer than 30 days;
- value is a signed claim `{ role: "owner", v: 1, exp }`, HMAC-signed with
  `OWNER_SESSION_KEY`;
- nothing in the claim or the cookie is bound to an IP address, a user-agent, a
  browser fingerprint or a device id.

Every later request verifies the signature and the expiry only. That is what makes it
survive travelling, switching networks and changing browsers; the code is the recovery
path in a browser with no valid session. A companion route that clears the cookie is
fine but not required.

## 5. Where the decision is made

One place. Find the single point where the existing gate decides whether a request may
proceed, and make the role part of that decision. Do not add a second parallel check,
and do not special-case owner inside individual features.

The client may render an owner badge from the session, but the client never decides
entitlement. No request is ever trusted because it claims a role.

## 6. What owner may bypass, and what it must not

May bypass, for the owner's own use — commercial restrictions:

- the paywall and the packet limit;
- per-day quotas and seat limits;
- demo and content-creation limits;
- export or watermark restrictions on content the owner created.

Must not bypass, ever — security controls:

- authentication or authorisation of any other user;
- admin-key gates on destructive routes;
- rate limits and abuse ceilings;
- audit logging — owner actions are logged, under a distinct actor, so the owner's
  traffic is separable from customers';
- per-customer data isolation;
- legal or contract gates that apply to everyone.

Owner usage gets its own counters rather than an exemption from counting, so a leaked
code shows up as anomalous usage instead of invisible usage.

## 7. Prohibited implementations

- the code in a query string, path or fragment;
- the code in `localStorage`, `sessionStorage`, IndexedDB or a URL the user can share;
- the code compiled into the client bundle, a build constant or an HTML attribute;
- entitlement derived from a body field, a header or a stored flag the client controls;
- logging the code or the session token;
- an IP allowlist or user-agent match standing in for the credential;
- writing `owner` onto a customer record as a plan;
- a per-feature bypass instead of the single gate.

## 8. Rotation and revocation

- New code: replace `OWNER_ACCESS_CODE`. Existing sessions continue until they expire.
- Invalidate every session at once: rotate `OWNER_SESSION_KEY`.
- Invalidate every session without touching either secret: bump the version claim and
  reject anything below the current value.

Revocation must be immediate and global; there is no per-device registry to clean up.

## 9. Acceptance tests

A change is not done until these pass against the running worker, with the negative
cases included:

1. No credential → `401`, no cookie, no detail about whether owner access exists.
2. Wrong code → `401`, generic code, no cookie; repeated attempts are rate-limited.
3. Right code → session cookie set, with `HttpOnly`, `Secure`, `SameSite=Lax`.
4. Request with the session → the specific gated feature opens, named explicitly in
   the test.
5. Tampered signature → `401`, no capability.
6. Expired session, and a session below the current version → `401`.
7. Code in a query string → not honoured.
8. A customer gains nothing: no header, a forged `role=owner` body field, a forged
   storage flag, a replayed cookie from another account.
9. Founder and Professional behaviour is unchanged — their existing tests still pass,
   unmodified.
10. The owner cannot read or write another customer's records.
11. Owner actions appear in the audit log under a distinct actor.

## 10. Reporting status

Per `docs/MIND-AUTHORITY.md`, the status is one of three:

- **instructed** — this document exists (it does, now);
- **implemented** — the `ezxhibitz` source contains the role, the constant-time
  comparison, the signed session and the single-gate decision, with the tests above;
- **conforming** — the deployed worker has been exercised and behaves as §9 describes.

The first implementation step is a read-only inventory of the gate: its route names,
its storage, its tier vocabulary (Founder, Professional), where it currently decides
access, and whether that is one choke point or several. This document deliberately
does not guess any of those.
